# 笔记与静态素材：重构设计（只设计，不含实现）

> 起因：现在一份笔记只能是 note 空间里的一个 `note.md`，`.md` 与它的素材被强行分开之后，
> 形如 `![](./img/a.png)`、`![](../assets/b.png)` 的引用自然全部失效。
> 本文回答两个问题（`.git` 能不能挪走 / 搬 .md + 指针行不行），给出三种可选模式、推荐方案、
> 以及落地所需的改动面。**不含实现**。

---

## 0. 先摆事实（都是在本机实测出来的，不是推断）

| 事实 | 依据 |
| --- | --- |
| 素材 RPC 现在**以笔记目录为基准**解析相对路径 | `asset` 里 `fs.resolve(p, { cwd: paths().dir })` |
| 素材 RPC **并不受"只能在笔记目录内"限制** | 实测：读笔记目录内 ✓、读工作区内别处 ✓、**读 `C:/Windows/win.ini` 也成功** ✓ |
| 所以"读不到图片"不是权限问题，而是**相对位置被破坏** | 上面两条合起来 |
| 每份笔记一个独立仓库，仓库在 `<笔记目录>/.git` | `ensureGit()` / `runGitIn(dir, …)` |
| git 支持"仓库与工作区分离" | `git --git-dir=<仓库> --work-tree=<工作区>`，或仓库配置里写 `core.worktree` |
| `.lnk` **不能**被程序透明读取 | 它只是 Explorer 的快捷方式，任何读取 API 都打不开它 |

**结论一**：问题不在 `.git` 在哪，而在 **`.md` 和它的素材之间的相对位置**。
**结论二**：方向 1（`.git` 外置）**可行**，但它只在"让 `.md` 留在原地"时才顺带解决问题 —— 真正起作用的是下面的**模式 B**。

---

## 1. 三种模式（每种都保持"一份笔记一个独立 git 仓库"）

### 模式 A：自包含（现状的改进版）——**建议做默认**
```
<工作区>/dsh-window/note/<会话>/<笔记名>/
  note.md            ← 正文
  assets/…           ← 素材「镜像」：按原目录里的相对结构复制进来
  .git/              ← 这份笔记自己的仓库（不变）
  .note-state.json   ← 标记
  .note-view.json    ← 阅读位置
```
- **导入文件夹时的做法**：从 `.md` 里扫描本地引用（`![](…)`、`<img src=…>`、`[x](…)` 里的图片后缀），
  连同它们所在子目录一并**按原相对路径**复制进 `assets/`，然后**只重写这一次引用前缀**
  （`./img/a.png` → `./assets/img/a.png`）。
- 好处：**一份笔记一个目录、一个仓库**，天然自包含、可整包搬走、可给别人；
  相对路径在笔记内部**依然成立**（因为相对结构被保留了）；素材也进了版本历史（图片的增删可回溯）。
- 代价：**复制一份**（磁盘翻倍；可选优化：同盘时用硬链接，NTFS 支持，不需要管理员）。
- 什么时候不合适：素材目录几个 GB、或素材在别的盘/网络盘。

### 模式 B：就地托管（in-place）——**方向 1 的正确用法**
```
<原来的目录>/
  note.md            ← 正文仍然在这里，和素材在一起（相对路径天然成立）
  img/…、assets/…     ← 原样不动，一个字节都不复制
  …其它文件           ← 与笔记无关，绝不提交

<工作区>/dsh-window/note/<会话>/<笔记名>/     ← 只放元数据 + 仓库
  <笔记名>.git/       ← 这份笔记自己的仓库，core.worktree 指回原目录
  .note-state.json
  .note-view.json
  link.json           ← { workTree: "<原目录>", noteFile: "note.md" }
```
- 做法：仓库用 `git --git-dir=<笔记空间>/<名>.git --work-tree=<原目录>`（或在该仓库里写 `core.worktree`），
  `runGitIn` 只需多带两个参数；**依然是一份笔记一个独立仓库**。
- 好处：**零复制、相对路径完全原生**、笔记在别的编辑器里也照样正常显示图片（因为我们没动它）。
- 必须处理的坑：
  1. **提交范围**：工作区是用户的目录，`git add -A` 会把整个目录吞进仓库 ✗。
     → 只 `git add` **正文 + 被引用的素材**（或先写 `info/exclude` 排除其余），并在 `note_diag` 里显示"本笔记跟踪 N 个文件"。
  2. **原目录被移动/删除**：笔记变"断链"。→ 状态里显式标记「素材目录不可达」，卡片给出「重新指定目录」，不静默失败。
  3. **可移植性**：把笔记空间拷到别的机器后，指针失效（指针是绝对路径）。→ `link.json` 里同时存**工作区相对路径**（能算出来时）+ 绝对路径，搬家后优先按相对路径找回。

### 模式 C：指针模式（方向 2：搬 .md + 前缀解析）
```
<笔记空间>/<会话>/<笔记名>/
  note.md            ← 从原目录「剪切」过来的正文副本
  .note.json（或会话状态里）: assetRoot = "<原目录绝对路径>"
  .git/
```
- 解析顺序：**笔记目录 → `assetRoot` → 工作区**；`asset` 增加一个 `root` 参数，
  或由 host 自己按这个阶梯找，命中即返回，并在返回里带上"实际命中路径"（便于排查）。
- 结论：**可行**，而且不需要 `.lnk` 参与 —— 指针写在元数据里更稳（跨平台、可被 agent 读到、可校验）。
- 代价：
  - 原目录里那份 `.md` 从此**不是**你在应用里改的那份（两边会分叉）→ 适合"原始素材只读、笔记在我这边写"的场景；
  - 笔记离开本机后素材全断（除非素材一起搬）；
  - 引用解析要"前缀化"，在别的编辑器里打开这份 `.md` 依然看不到图（它已经不在原目录了）。
- **`.lnk` 的正确定位**：可以在原目录里放一个快捷方式当**面包屑**（"这份笔记现在住在这里"），
  但它**不能**作为解析依据（程序读不了它）。同理：Windows 的符号链接要开发者模式/管理员，
  目录联接（junction）对文件不适用 —— 所以别把方案压在链接文件上。

## 2. 推荐

1. **默认走模式 A**（自包含 + 素材镜像）：它同时满足"一份笔记一个仓库"和"素材找得到"，
   而且笔记可整包搬走 —— 这正是 `.md + 素材` 的核心竞争力。
2. **给一个模式 B 的开关**（`就地托管`）：素材很重、或素材在别的盘时用；
   git 的隔离靠"只提交正文 + 被引用素材"来保证。
3. **模式 C 只作为一种导入选项**（"链接到原目录，不复制"）保留，
   它的价值是"原目录只读、笔记单独写"，但要在 UI 上把"两边会分叉"写清楚。
4. 三种模式**对外表现一致**：卡片上永远显示「素材：自带 / 就地 / 指针」+ 实际路径，
   `note_diag` 里给出可点击的路径与实际命中结果。

## 3. 落地需要的改动面（供排期）

| 层 | 改动 | 量级 |
| --- | --- | --- |
| 笔记元数据 | `note.json`（或会话状态）新增 `assetRoot` / `workTree` / `mode`（A/B/C） | 小 |
| 导入 | 新增 **导入文件夹**（选 `.md` → 扫描本地引用 → 模式 A 复制镜像并改写前缀 / 模式 C 只记指针） | 中 |
| 素材解析 | `asset` 支持 `root` + 阶梯查找；返回命中路径与实际基准 | 小 |
| 客户端 | `![](…)` 解析改用"笔记给出的基准"；失败时显示"找不到：<原路径> + 试过哪些基准" | 小 |
| git | `runGitIn` 支持 `--git-dir/--work-tree`；模式 B 下只提交正文与被引用素材 | 中 |
| 断链处理 | 状态里标「素材目录不可达」+ 卡片给「重新指定」 | 小 |
| 工具面 | `note_create {folder, file, mode}`、`note_asset_root`（查询/修改，改动要显式）、`note_diag` 增补 | 小 |
| 性能 | 大图/多图仍走 base64 会重；建议**加一个 HTTP 素材路由**（`/plugins/dsh-window/asset?note=…&path=…`，带缓存头），vendor 路由已经是现成先例 | 中 |
| 安全 | `assetRoot` 一旦可被**模型**单方面放大，就等于把整台机器的读权限给了卡片 → 只允许**用户显式**指定，改动写进会话状态并显示在卡片上 | 小但重要 |
| 迁移 | 既有笔记全部按模式 A（现状即 A 的退化情形：素材放笔记目录里）→ 无需迁移 | — |

---

## 4. 待你定的两件事

1. **默认模式**：我建议 A（自包含、可搬走）；若你的素材普遍很重，则默认 B。
2. **导入文件夹时**：素材是**复制一份**（A）还是**就地引用**（B/C）？
   可以做成导入时的一个勾选项，但默认值要定一个。
